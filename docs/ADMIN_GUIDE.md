# FresherPrep Administrator Guide

This guide documents the Admin UI and backend behavior currently implemented in FresherPrep. It does not describe planned modules. All management actions require an authenticated account with role `ADMIN`; the backend enforces this independently of the frontend navigation.

## 1. Accessing Admin

Open `/admin` or select **Admin** from the authenticated application. The Admin shell verifies the current session and role before rendering. A normal `USER` is redirected from the Admin UI and receives HTTP 403 when directly calling protected backend operations.

The current Admin navigation contains:

- Overview
- Knowledge
- Learning paths
- Lessons
- Questions
- Quizzes

The Users navigation entry is currently disabled. The backend has a role-update operation for a known user ID, but there is no implemented Admin user-list/role-management screen; do not treat the disabled entry as an available workflow.

## 2. Admin dashboard

### Purpose

The Overview page provides compact content counts and status totals using existing backend resources. It is operational visibility, not a product analytics system.

### Usage

Open `/admin`. Cards link to the corresponding management areas. If an individual metric cannot load, the dashboard reports unavailable data rather than inventing a value.

### Notes

- Counts reflect content accessible through current Admin APIs.
- The page does not expose learner passwords, refresh tokens, or secret configuration.
- Use the individual management pages for editing; the Overview itself does not mutate content.

## 3. Shared content concepts

### Status lifecycle

Content uses these statuses where supported:

- `DRAFT`: editable working content, not learner-visible.
- `REVIEW`: content prepared for review/publishing.
- `PUBLISHED`: available to the relevant learner flow when parent/reference rules are also satisfied.
- `ARCHIVED`: retained but removed from normal learner discovery.

Publishing runs domain validation. For example, a published child requires the relevant published parent, a quiz requires valid questions/rules, and a question publishes a specific version. Archiving does not erase historical QuizAttempt snapshots.

### Delete versus archive

Delete is intentionally narrower than archive. Content with history, dependent relationships, published children, progress, attempts, or configured references may be rejected by the backend. In those cases archive the content or remove safe configuration references first.

### Generated and editable identities

Database UUIDs are always system-managed and never form inputs.

The current identity behavior is:

- Knowledge slug: generated by backend on create and immutable through ordinary update.
- Lesson slug: generated by backend on create and immutable through ordinary update.
- Question code: generated by backend on create and immutable through ordinary update.
- Learning Path slug: currently an explicit editable Admin field.
- Quiz code: currently an explicit editable Admin field with uniqueness validation.

Generated slugs/codes use a readable base and a five-character alphanumeric suffix, for example `java-oop-a7k2p`. The suffix reduces collisions; repository checks and database unique constraints remain authoritative. Existing identity values and references are preserved when names/titles change.

## 4. Knowledge management

### 4.1 Purpose and access

Open `/admin/knowledge` to manage the curriculum hierarchy:

```text
TECHNOLOGY -> CATEGORY -> TOPIC -> SUBTOPIC
```

The page displays the hierarchy as an indented tree and supports search by name, generated slug, or type.

### 4.2 Fields

- **Node type**: `TECHNOLOGY`, `CATEGORY`, `TOPIC`, or `SUBTOPIC`.
- **Parent**: required according to the four-level relationship; Technology is a root.
- **Name**: learner/admin-facing name, maximum 150 characters.
- **Display order**: non-negative ordering value among related content.
- **System slug**: read-only after creation. It is not sent by create/update forms.
- **Status**: draft/review/published/archived.

### 4.3 Creating a node

1. Select **New node**.
2. Choose the node type.
3. Select the required parent for non-root types.
4. Enter the name and display order.
5. Select **Create node**.

The backend validates the parent type, generates the unique slug, creates the node as domain-defined initial status, and returns the saved identity. The form then displays that slug as read-only.

### 4.4 Editing and moving

Select a tree item, change name, type/parent placement where valid, or display order, and save. Ordinary editing keeps the slug stable. A type/parent change is rejected when it would make existing children invalid, create an illegal hierarchy, or put published content below an unpublished parent.

### 4.5 Publish, archive, and delete

Use the status actions shown below the form. A node cannot publish beneath an unpublished parent. A parent with published children cannot be archived first. Delete is allowed only for draft/archived nodes without children or protected references.

### 4.6 Validation and common mistakes

- Missing parent: select the expected parent type.
- Incorrect hierarchy: Category belongs to Technology, Topic to Category, Subtopic to Topic.
- Negative order: use zero or a positive number.
- Publish failure: publish ancestors first.
- Archive failure: archive published children first.
- Delete failure: move/delete children and remove safe references first.
- Do not attempt to edit a slug through HTTP; the update DTO does not accept it.

## 5. Learning Path management

### 5.1 Purpose and access

Open `/admin/learning-paths` to create an ordered curriculum associated with a Technology and configure its lesson items.

### 5.2 Path fields

- **Name**: display name.
- **Slug**: currently entered manually; lowercase letters, numbers, and single hyphens are expected and uniqueness is enforced.
- **Technology**: selected on creation and fixed by the current update contract.
- **Status**: draft/review/published/archived.

### 5.3 Creating and editing

1. Select **New learning path**.
2. Enter name and slug.
3. Select a Technology.
4. Create the path.
5. Select the saved path to configure items.

Editing updates name and slug but not Technology. A duplicate slug is rejected as a conflict. After saving, list and detail data are reloaded.

### 5.4 Learning Path items

Each item links one Lesson to the path and contains:

- **Display order**: curriculum sequence.
- **Required**: whether the lesson participates in required completion.
- **Weight**: positive contribution used by backend progress calculation.

Use **Add lesson** to create an item. The same lesson cannot be added twice to one path. Existing items can update order, required flag, and weight, or be removed.

The learner-facing path sorts items by display order. Backend path progress uses required items and weights; do not assume a simple completed-count percentage when weights differ.

### 5.5 Publishing, archiving, deleting, and mistakes

Publishing validates the path's Technology and lesson configuration according to the service rules. Learners can discover/join only published paths. Archiving removes the path from normal public discovery but keeps existing relationships/history.

Delete is restricted to safe statuses and is rejected when protected membership or item state makes deletion unsafe.

Common mistakes:

- Reusing an existing slug.
- Adding the same lesson twice.
- Reusing a display order already occupied by another item.
- Entering zero/negative weight.
- Publishing while required referenced content is not in an allowed state.

## 6. Lesson management

### 6.1 Purpose and access

Open `/admin/lessons`. Lessons are primarily organized by their parent `SUBTOPIC`, matching the domain relationship.

The left panel workflow is:

```text
Select parent Subtopic
-> load one server-paginated lesson page
-> optionally search the loaded group page
-> create or select a lesson
```

Changing Subtopic resets page/search/selection. The main list uses 20 lessons per server page rather than loading the whole lesson database.

### 6.2 Fields

- **Subtopic**: selected by the parent context. Create/update requests use that selected context.
- **Title**: maximum 200 characters.
- **System slug**: backend-generated from title plus a five-character suffix; read-only and stable after creation.
- **Display order**: non-negative position within content organization.
- **Minimum read seconds**: retained as lesson metadata/analytics configuration. It no longer blocks lesson completion.
- **Required scroll percent**: 1-100; used for reading qualification and for completion when no assessment exists.
- **Content**: required lesson content string rendered by the learner reading experience.
- **Status**: draft/review/published/archived.

### 6.3 Creating a lesson

1. Select a Subtopic first.
2. Select **New lesson**.
3. Enter title, content, display order, tracking value, and scroll requirement.
4. Save.

The backend verifies that the parent is a Subtopic, generates a unique slug, and returns the detail. The list is refreshed in the same parent context.

### 6.4 Editing

Select a lesson in the scoped list. Update fields and save. The current parent selector is the management context; slug cannot be overwritten. Published lessons cannot be placed beneath an unpublished Subtopic.

### 6.5 Prerequisites

The Prerequisites card lists existing prerequisite lessons. Add a prerequisite by selecting another lesson. The backend rejects:

- self-reference;
- duplicate edges;
- cycles;
- nonexistent lessons.

Remove an edge with **Remove**. This changes only the prerequisite relationship, not either Lesson record.

### 6.6 Lesson Assessment

The Assessment card assigns at most one Quiz to a Lesson. A valid assessment:

- is a `LESSON` quiz;
- uses an 80% pass threshold;
- has FIXED questions or RULE_BASED scope matching the Lesson Subtopic;
- satisfies published-reference rules when applicable.

The current service does not replace an existing assignment in one operation. To change the assessment, remove the current relationship first, then assign the new Quiz. Removing the relationship does not delete the Quiz or its historical attempts.

For learners, a passing assessment is the completion authority regardless of active reading time. Without an assessment, scroll qualification remains the completion behavior.

### 6.7 Publish/archive/delete and mistakes

Publish only after parent/content prerequisites satisfy backend validation. Archive is safer than deletion when progress, path items, prerequisites, or assessment references exist. Delete is allowed only in safe status/reference conditions.

Common mistakes:

- Creating without first selecting a Subtopic.
- Treating minimum read seconds as a pass requirement; it is informational tracking metadata.
- Assigning a non-LESSON quiz or one with a threshold other than 80%.
- Assigning questions from another Subtopic.
- Expecting title edits to regenerate the stable slug.

After every successful save/mutation, the UI reloads affected list/detail information and shows success feedback.

## 7. Question management

### 7.1 Purpose and access

Open `/admin/questions`. A logical Question owns immutable QuestionVersions, and each version owns four QuestionOptions.

Questions are primarily grouped by parent Subtopic:

```text
Select parent Subtopic
-> server-side page of questions
-> optional difficulty/status filter
-> local search in the loaded page
-> edit metadata or version history
```

The main list is paginated at 20 questions per page. Language/category are question metadata, not mandatory list-navigation filters.

### 7.2 Logical Question fields

- **Subtopic**: supplied by selected parent context.
- **System code**: generated from the Subtopic slug plus a five-character suffix; read-only and stable.
- **Difficulty**: `EASY`, `MEDIUM`, or `HARD`.
- **Language**: `VI` or `EN`.
- **Category**: `TECHNICAL`, `GRAMMAR`, `VOCABULARY`, or `TOEIC`.
- **Status**: draft/review/published/archived.
- **Published version**: pointer to the exact version currently used by new attempts.

### 7.3 Creating and editing metadata

1. Select a Subtopic.
2. Select **New question**.
3. Choose difficulty, language, and category.
4. Create the logical Question.
5. Add its first version.

Because a logical Question has no content/title before its first version, the backend uses the Subtopic slug as the readable code base. The frontend cannot send or overwrite code.

Metadata updates preserve the code. Publishing requires a published Subtopic and a valid selected version.

### 7.4 Versions

A version contains:

- version number;
- question content;
- overall explanation;
- exactly four options.

The first/new-version form calculates the expected next number, while the backend verifies it. Existing versions are not edited in place. **Create revision** copies the selected version into a new editor; saving creates the next immutable version.

This rule protects attempt history: `QuizAttemptQuestion` stores the exact `question_version_id`, so later revisions cannot change old question text, options, grading, or results.

### 7.5 Options and explanations

Every version requires exactly four positions, 1 through 4, with:

- nonblank option content;
- one and only one correct option;
- an explanation for each option;
- a nonblank overall question explanation.

The Admin editor uses one radio selection for the correct option. Backend validation repeats these checks; client validation alone is not trusted.

### 7.6 Publishing, archive, delete, and mistakes

Select **Publish** on a specific version. That operation sets `published_version_id` and makes the logical Question published according to domain rules. Existing attempts continue using their old snapshot.

A Question with version history cannot be hard-deleted. Questions referenced by fixed quizzes also cannot be deleted. Archive the Question when history must remain.

Common mistakes:

- Forgetting to create a version after creating metadata.
- Supplying fewer/more than four options.
- Marking no option or multiple options correct.
- Reusing/skipping option positions.
- Trying to edit a published version instead of creating a revision.
- Expecting a new version to alter an already started QuizAttempt.

## 8. Quiz management

### 8.1 Purpose and access

Open `/admin/quizzes` to configure general quizzes and Lesson assessments. The page lists quiz metadata and opens mode-specific configuration after selection.

### 8.2 Fields

- **Code**: required, unique, manually editable in the current Quiz Admin implementation.
- **Title**: learner-facing title.
- **Type**: `LESSON`, `TOPIC`, `MIXED`, or `READINESS`.
- **Selection mode**: `FIXED` or `RULE_BASED`.
- **Language**: `VI` or `EN`.
- **Category**: technical/grammar/vocabulary/TOEIC/mixed as allowed.
- **Pass percentage**: 0-100 for general quizzes; Lesson Assessment assignment requires exactly 80.
- **Maximum score**: positive score scale. Passing score is derived from maximum score and percentage.
- **Time limit**: optional minutes, persisted as duration seconds. Blank means no countdown.
- **Status**: draft/review/published/archived.

Changing type, mode, language, or category can require removing existing rules/fixed questions first. A Quiz already assigned as a Lesson Assessment must remain a LESSON quiz with 80% threshold.

### 8.3 FIXED quizzes

Add published-compatible Questions and assign each a positive, unique display position. The same Question cannot appear twice. Lesson/Topic quiz types also enforce compatible knowledge scope. Remove fixed questions while the Quiz is in an editable status.

At attempt start, the backend takes the currently published version of each configured Question in fixed order and snapshots it into the attempt.

### 8.4 RULE_BASED quizzes

Each rule specifies:

- Knowledge scope.
- Optional difficulty.
- Positive question count.

Rules cannot overlap in a way that makes selection ambiguous. Lesson quizzes select a Subtopic; Topic quizzes select Topic/Subtopic according to domain validation; mixed quizzes can combine suitable scopes.

Publishing checks that enough eligible published Questions exist for every rule. Starting also rechecks availability. If a rule requests more Questions than available, the backend rejects the start rather than creating an incomplete attempt.

### 8.5 Creating, editing, publishing, and deleting

1. Create metadata in DRAFT.
2. Add fixed questions or selection rules.
3. Move to REVIEW.
4. Publish after validation succeeds.
5. Archive when it should no longer be started.

Delete is allowed only for safe draft/archived quizzes without attempt history or Lesson Assessment references. Remove configuration/reference relationships first where appropriate.

Common mistakes:

- Duplicate code.
- Publishing an empty fixed quiz.
- Publishing rule-based configuration with insufficient eligible questions.
- Mixing question language/category with incompatible quiz metadata.
- Assigning duplicate positions or overlapping rules.
- Changing pass threshold away from 80 after Lesson Assessment assignment; backend rejects it.

## 9. User and role management status

The current backend can update a role for a known user ID and protects that operation with `ADMIN`. However, the product does not currently provide an Admin user listing/search/edit page; `/admin/users` is disabled in navigation.

Therefore there is no documented UI procedure for browsing users or changing roles. Do not expose direct role-update calls to ordinary users, and do not manually edit role data in the database as an Admin workflow.

## 10. Validation, authorization, and error handling

Admin controllers delegate to services; business rules are not trusted to frontend controls. Services use `@PreAuthorize("hasRole('ADMIN')")` for content mutation/read operations. Invalid operations produce standardized HTTP errors:

- 400: malformed/invalid values.
- 401: missing or invalid authentication.
- 403: authenticated but not authorized.
- 404: requested resource not found.
- 409: duplicate data or invalid state transition/conflict.

Database messages, SQL, stack traces, credentials, and token hashes are not included in normal API errors.

## 11. Operational troubleshooting

### Save returns conflict

Check unique slug/code, duplicate item/question/rule relationships, status restrictions, or protected history. For generated Knowledge/Lesson/Question identity, retry creation only if the server reports a conflict; do not invent an identity client-side.

### Publish fails

Read the business error and verify parents, referenced lessons/questions, published versions, and quiz capacity. Publishing is deliberately stricter than saving a draft.

### Delete fails

Prefer archive. A rejected delete usually protects child content, path membership/items, progress, prerequisite edges, question versions, quiz attempts, or assessment references.

### A learner cannot see content

Verify the content and required parent chain are PUBLISHED. For quizzes, verify valid published question versions. For paths, verify the path itself is published and its lesson items are correctly configured.

### Lesson completion is unexpected

For a Lesson with Assessment, inspect the user's submitted attempts for that assessment quiz: 80% or greater completes the Lesson, regardless of active time. For a Lesson without Assessment, inspect scroll qualification. `minimumReadSeconds` is not a completion gate.
